# Журнал решений

Нумерация своя, не wsldrive. Где решение взято оттуда, это сказано.

## Р-001. Две программы: сервер в WSL на Go, окно в Windows на Tauri
**2026-10-07 · принято**

Туннели нужны внутри WSL (там работают программы, которые к ним подключаются,
и там же ключи ssh), а управлять ими удобно из Windows. Ни одна сторона не
дотягивается до другой напрямую, поэтому их две и говорят они по HTTP.

Сервер — обычная программа Linux без зависимостей кроме `ssh`: работает и без
окна, и вне WSL. Окно — по образцу wsldrive-gui: Tauri 1, страница на Alpine,
Tailwind и Flowbite из `ui/vendor`, минимум пакетов Rust.

## Р-002. Сервер держит сторож из Windows, а не systemd
**2026-10-07 · принято**

Проверено в wsldrive (Р-042 там): WSL убивает всё, что запущено вызовом
`wsl.exe`, когда тот выходит, — даже отвязанное через `setsid` и `nohup`. Без
открытых сеансов WSL и вовсе усыпляет машину через несколько секунд, systemd в
ней или нет. Служба systemd поэтому не решает задачу «туннель есть всегда»: после
входа в Windows WSL не запущена вовсе, а запущенная — засыпает.

Решение — сторож: тот же `hotpipe-gui.exe` с ключом `--keeper`, без окна. Он
держит открытым `wsl.exe -e hotpipe-server`, ждёт его выхода и запускает снова —
после падения, убийства, `wsl --shutdown`. Сервер, поднятый руками в WSL, сторож
не дублирует: видит, что API отвечает, и только присматривает.

- **Один сторож** — замок `keeper.lock`, открытый без совместного доступа. Замок
  снимает Windows, когда процесс уходит, даже убитый: застрявших не бывает.
- **Выключение запоминается** — `server_enabled` в `gui-config.json`. Окно
  сначала записывает желание, потом просит сервер завершиться; сторож, увидев
  желание, уходит. В обратном порядке сторож успел бы поднять сервер снова.
- **Повторы** — 2, 5, 10, 30, 60 с, если сервер не прожил и 30 секунд: нет файла
  или испорчены настройки — дёргать WSL каждую секунду незачем.
- **Сторож — в том же файле, что и окно**, а не третья программа: тот же каталог,
  те же настройки, одна раскладка. Ветвление идёт до запуска Tauri, так что
  WebView2 сторож не трогает.

Проверено 2026-10-07: `kill -9` сервера — сторож поднял его за 6 с (из них 5 —
пауза повтора); второй сторож ушёл сам; выключение переключателем гасит сервер,
туннели и сторожа, включение возвращает всё.

## Р-003. ssh — дочерний процесс без -f, с BatchMode и ExitOnForwardFailure
**2026-10-07 · принято**

| Ключ | Зачем |
|---|---|
| без `-f` | ssh остаётся дочерним: видны выход, вывод и pid |
| `BatchMode=yes` | пароль спросить некого; без этого ssh висел бы, ожидая ввода |
| `ExitOnForwardFailure=yes` | без него ssh с занятым портом живёт без туннеля |
| `ControlMaster=no`, `ControlPath=none` | общее соединение из `~/.ssh/config` сделало бы наш ssh клиентом чужого процесса |
| `StrictHostKeyChecking=accept-new` | новый хост запоминается, подменённый ключ отвергается |
| `ServerAliveInterval=5`, `CountMax=3` | обрыв замечается за 15 с; `=1` из привычной команды рвёт туннель на секундной заминке |
| `--` перед хостом | что бы ни оказалось в имени хоста, ключом ssh его не поймёт |

ssh запускается в своей группе процессов (сигнал доходит и до `ProxyCommand`) с
`Pdeathsig=SIGTERM`: упади сервер — ssh уйдут за ним и не будут держать порты.

## Р-004. «Поднят» — это «сам ssh слушает порт», по /proc
**2026-10-07 · принято**

Очевидная проверка — подключиться к локальному порту — здесь вредна: ssh
передаёт подключение на ту сторону, и каждая проверка была бы настоящим
соединением с удалённой службой. MySQL считает такие оборванные соединения
ошибками и после `max_connect_errors` блокирует адрес — а адресом для неё был бы
её же 127.0.0.1.

Вместо этого: номера сокетов из `/proc/<pid>/fd` против слушающих сокетов порта
в `/proc/net/tcp{,6}`. Заодно отличаем «наш ssh слушает» от «порт слушает
кто-то другой».

Связь с сервером проверяет сам ssh (`ServerAlive*`) и выходит при обрыве. Если
порт пропал, а ssh жив, — даём ему секунду выйти самому (его объяснение лучше
нашего), потом убиваем.

## Р-005. Повторы с нарастающей паузой; чужой порт не трогаем, свой сирота — убираем
**2026-10-07 · принято**

Паузы 1, 2, 5, 10, 30, 60 с. Простоявший минуту туннель после обрыва снова
чинится за секунду. Сервер, отвергающий ключ, не дёргается чаще раза в минуту.

Порт проверяется до запуска ssh: занятый порт ssh всё равно не откроет, а лишний
вход на сервер оставит след в чужом журнале. Держатель порта называется по имени
и pid. Чужой процесс, например ssh, поднятый руками, не трогается никогда.

Наш ssh помечен переменной окружения `HOTPIPE_TUNNEL=<pid сервера>:<id>`.
Завершается он, только если осиротел — его родитель уже не записанный в метке
сервер (умерший сервер передаёт детей init). Одной метки мало: первая версия
убивала любой помеченный ssh, и прогон проверок, поднявший свой сервер, уронил
настоящий туннель на 5001. Так же второй экземпляр сервера ронял бы туннели
первого. Теперь ssh живого сервера называется в ошибке и не трогается.

## Р-006. API: только 127.0.0.1, заголовок X-Hotpipe, проверка Host и полей
**2026-10-07 · принято**

API на петлевом адресе виден любой программе на машине, в том числе странице в
браузере: простой POST браузер отправит без спроса. А поля туннеля попадают в
командную строку ssh — хост `-oProxyCommand=…` был бы запуском произвольной
команды.

- изменяющие запросы требуют заголовка `X-Hotpipe`: нестандартный заголовок
  заставляет браузер спросить разрешения (CORS), а мы его не даём;
- `Host` должен быть `127.0.0.1`, `localhost` или `::1` — против DNS rebinding;
- хост, пользователь, адреса и путь к ключу проверяются по белым спискам знаков,
  минус в начале запрещён, перед хостом стоит `--`;
- произвольных ключей ssh в туннеле нет намеренно.

## Р-007. Туннели живут у сервера; окно своего учёта не ведёт
**2026-10-07 · принято**

Как в wsldrive (Р-040 там): два списка одних и тех же туннелей рано или поздно
разошлись бы. Окно показывает `/api/status` как есть и отправляет правки в API.
Сервер записывает файл до того, как применить правку к работающим туннелям: после
перезапуска он поднимет ровно то, что показывал.

Включён туннель или нет — тоже в файле: выключенный руками туннель не поднимется
сам после перезагрузки.

## Р-008. Автозапуск — строка в HKCU\…\Run, ведущая к сторожу
**2026-10-07 · принято**

После входа в Windows нужны работающие туннели, а не окно на экране, поэтому
запускается сторож. Раздел текущего пользователя — права администратора не нужны.
Пишется через `reg.exe`: библиотека реестра ради одной строки — лишние пакеты.
Окно сверяет записанную команду со своим путём и предлагает переписать, если
папку переложили.

Планировщик заданий дал бы перезапуск при сбое, но сторож перезапускает сервер
сам, а сторожу падать не с чего: он ждёт процесс и спит.

## Р-009. Версия, сборка и раскладка — как в wsldrive
**2026-10-07 · принято**

- Версия `0.1.<число снимков>-alpha`, одна на все программы; окно сверяет свою с
  серверной и предупреждает о расхождении. Вне git-хранилища — `0.1.0-alpha`,
  снимок «вне-хранилища», пометка `[изменённое дерево]`.
- Результаты сборки — в `build/`, в хранилище не попадают; выпуски — в `dist/`.
- Окно собирается на Windows через местную копию (`cache\gui-build`): cargo не
  работает на `\\wsl.localhost`. Сценарии PowerShell — с меткой BOM, иначе
  PowerShell 5.1 читает кириллицу как ANSI.
- Окно раскладывается на местный диск: с `\\wsl.localhost` каждый запуск
  упирается в вопрос о непроверенном издателе, да и автозапуск должен вести к
  файлу, доступному до старта WSL.
- Сервер ставится в `~/.local/bin` через `install` (новый файл и
  переименование): пересборка не подменяет файл под работающим процессом.

Выяснилось при первой сборке: `git … 2>$null` при `ErrorActionPreference =
Stop` в PowerShell 5.1 бросает исключение, и вне хранилища сборка обрывалась.
`version.ps1` выполняет git с `Continue`.

## Р-010. macOS: сервер держит launchd, всё — в одном HotPipe.app
**2026-10-10 · принято**

В macOS нет WSL, и причины сторожа (Р-002) пропадают: сервер — обычный
процесс, а поднимать его при входе и после падения умеет launchd. Поэтому:

- **Сторож — задание launchd** `dev.hotpipe.server` (LaunchAgent, `KeepAlive`,
  `RunAtLoad`). Описание лежит в `~/Library/Application Support/HotPipe/`,
  окно загружает его (`launchctl bootstrap`). Автозапуск — та же запись в
  `~/Library/LaunchAgents`.
- **Выключение** — `launchctl bootout` и `disable`: иначе `KeepAlive` поднял
  бы завершённый сервер, а автозапуск — при следующем входе. Включение снимает
  запрет. Перезапуск из окна выгружает и загружает задание заново, чтобы
  launchd прочёл новые путь и порт.
- **Пакет**: сервер едет в `HotPipe.app/Contents/MacOS/hotpipe-server`
  (`externalBin` у Tauri); окно берёт его, если путь в настройках пуст.
  Настройки и журнал окна — в `~/Library/Application Support/HotPipe/`: внутрь
  подписанного пакета писать нельзя. Туннели сервера — в
  `~/Library/Application Support/hotpipe/tunnels.json` (`os.UserConfigDir`).
- **«Поднят»** (Р-004) — по-прежнему «сам ssh слушает порт», без пробных
  подключений; вместо `/proc` спрашиваем `lsof -iTCP:<порт> -sTCP:LISTEN -a -p
  <pid>`. Раз в 2 с на туннель — дёшево (≈60 мс).
- **Метка ssh** (Р-005) — в аргументах, `-o Tag=hotpipe:<pid сервера>:<id>`:
  окружение ssh (программы Apple) macOS не отдаёт даже тому же пользователю.
  Tag ssh только запоминает для `Match tagged`; если в `~/.ssh/config` есть
  свой Tag, наш его перекроет.
- **Pdeathsig** в macOS нет. ssh упавшего сервера остаётся держать порт;
  launchd поднимает сервер, а тот убирает сироту по метке. Мягкое завершение
  (SIGTERM от launchd или /api/shutdown) останавливает ssh как и раньше.

Код по системам разведён файлами (`procnet_linux.go` / `procnet_darwin.go`,
`server.rs` / `server_macos.rs`), а не правкой общего: сборка для WSL не
меняется, и изменения из исходного хранилища вливаются без споров.
